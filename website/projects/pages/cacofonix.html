1 Introduction

This project is about building an app that plays local audio (music) files. My goals will be listed in depth later but basically I am aiming for a minimal (in the artistic sense) GUI with typical music-playing functionalities (e.g. shuffle, looping, volume etc.) and easily customisable organisation (e.g. albums, artists). I will be building this app specifically for my operating system of arch-linux. I have basically no experience with app development so this will be a very informal project and I will try to explain what I do and why. This project is titled phase 1 because if I finish this I will try to make a physical device to run the app and play music while out and about (an MP3 player).

1.1 Obtaining Music

The main ways of obtaining music files is either by digitising a CD, buying the music online (e.g. amazon music) or by downloading copyright-free music online. To avoid any copyright issues I have downloaded a selection of copyright-free classical music recordings using yt-dlp and ffmpeg. These packages make it easier to download and convert music. I decided to use opus file format because it takes less space and I'm building from scratch so there shouldn't be any compatibility issues. I downloaded the music using the yt-dlp <tags> <URL> command with the following tags (separated by spaces) : -x which only downloads audio; --audio-format opus; --audio-quality 128K which is the bitrate; --ppa "ExtractAudio+ffmpeg_o:-acodec libopus -af loudnorm" which is an ffmpeg command to normalise audio (long because it forces recompilation to opus as yt-dlp preferes to copy a file if it exists which messes up the audio normalisation). Also I had to write the tags out individually because I wasted far too long trying to get stylised code to wrap nicely on OpTeX and now here. I also messed around with downloading to specific files and auto-inserting metadata but decided it would be better to make a simple editor as part of the app.

2.1 File Playback

The code below was used to test simple mp3 file playback with a fixed path.

01 use rodio::{Decoder, OutputStream, Sink};
02 use std::fs::File;
03 use std::io::BufReader;
04 
05 fn main() {
06   let (_stream, stream_handle) = OutputStream::try_default().unwrap();
07 
08   let sink = Sink::try_new(&stream_handle).unwrap();
09 
10   let file = File::open("/home/bob/Music/Songs/tmp/test.mp3").unwrap();
11
12   let source = Decoder::new(BufReader::new(file)).unwrap();
13 
14   sink.append(source);
15 
16   sink.sleep_until_end();
17 }

At the top, the use lines are importing library commands to use. The rodio library adds audio handling commands. The main() function is called by default when the file is run. Line 06 tries to set up audio on the default device playback. I also learned that having _stream is for variables that need to be kept but not used, as if dropped audio would not play and if not marked with _ Rust would give a warning as it is not used directly. Line 08 declares the sink which is where the audio goes to be played. The & prefix for variables only lets the function look at the variable. If the variables was passed as is it would be moved from the current scope to the function scope and be inaccessible outside afterwards. Line 12 decodes the audio file. BufReader makes files process in chunks to reduce system calls so saves on resources. The unwrap() method was used on most commands temporarily which basically does if (error) {crash} else {return value}.

2.2 Persistent Background Daemon with Unix Communication

This one-time file execution test worked so the next step was to make it a background service (daemon) that listens for commands sent to it and interprets them. The code below starts a Unix Domain Socket (UDS) which is basically just a local file (in my case in /tmp/) that the daemon and client interact with to share data on the same machine. Initially I was creating a local server (over TCP) to communicate, but this wraps IP and Port on the data which is unnecessary for now with terminal commands. Once the UDS is running on one terminal, I can connect to it from a different terminal and send it commands (image after code). I used the netcat command nc -U /tmp/music-daemon.sock to connect to the socket. I also decided to switch from opus files to AAC files. This is because, although better, opus is quite a new format (2012) and is not yet natively supported by rodio. There was a rodio add-on magnum that allows opus decoding however it is 2 years old and required quite an old version of rodio that then didn't work correctly with pipewire / wireplumber (my local audio management system). Due to this I decided to switch to AAC format (.m4a extension) which is still better than mp3 but also old enough (1997) to be more universally supported than opus.

01 use rodio::{Decoder, DeviceSinkBuilder, Player};
02 use std::os::unix::net::UnixListener;
03 use std::io::{BufReader, BufRead};
04 use std::fs::File;
05 use chrono::Local;
06 
07 const SOCKET_PATH: &str = "/tmp/music-daemon.sock";
08 const MUSIC_PATH: &str = "/home/bob/Music/Songs/";
09 
10 fn main () {
11   
12   let stream_handle = DeviceSinkBuilder::open_default_sink().expect("Failed to open audio stream");
13   let player = Player::connect_new(stream_handle.mixer());
14 
15   let _ = std::fs::remove_file(SOCKET_PATH);
16   let listener = UnixListener::bind(SOCKET_PATH).unwrap();
17   println!("Daemon listening at {}", SOCKET_PATH);
18 
19   for stream in listener.incoming() {
20     let stream = stream.unwrap();
21     let reader = BufReader::new(stream);
22     for line in reader.lines() {
23       let line = line.unwrap();
24       handle_command(&line, &player);
25     }
26   }
27 
28 }
29 
30 fn handle_command (line: &str, player: &Player) {
31 
32   let time = Local::now().format("%H:%M:%S");
33 
34   let mut parts = line.splitn(2, ' ');
35   let command = parts.next().unwrap_or("");
36   let filename = parts.next().unwrap_or("");
37   let arg = format!("{}{}", MUSIC_PATH, filename);
38   
39   match command {
40 
41     "play" => {
42       match File::open(&arg) {
43         Ok(file) => {
44           match Decoder::new(BufReader::new(file)) {
45             Ok(source) => {
46               player.stop();
47               player.append(source);
48               player.play();
49               println!("[{}] Playing {}", time, arg);
50             }
51             Err(e) => println!("[{}] Failed to decode {} : {}", time, arg, e),
52           }
53         }
54         Err(e) => println!("[{}] Failed to load {} : {}", time, arg, e),
55       }
56     }
57 
58     "stop" => {
59       player.stop();
60       println!("[{}] Stopped", time)
61     }
62 
63     _ => println!("[{}] Invalid command : {}", time, command),
64 
65   }
66 
67 }

The rodio structs (library commands) changed name because I updated to a newer version. The chrono library allows time formatting. Both const and let are immutable by default in Rust; the difference is that instances of const are replaced by the value on compilation, whereas let creates an actual variable who's value is accessed during runtime. For a mutable variable let mut is used. The function .expect() is basically .unwrap() but with a custom error message so basically if (error) {console.log("You failed"); crash} else {continue}. In line 15 the variable _ is declared, which is a variable to be immediately dropped. This is needed because the remove_file() function returns a Result type (indicating succes Ok(T) or failure Err(E)) which should not be ignored (gives a warning). Assigning to _ acknowledges it the result then drops it because in this case it doesn't matter; the line deletes an existing socket file if it exists so if it doesn't exist it doesn't matter. Line 16 sets the unix connection file. Lines 19-26 basically read the socket for incoming data, read the data and pass it to the handle_command() function as a string to be interpreted. Line 34 splits the incoming string into at most 2 strings on the space character (using the splitn() function which creates an array with the iterator trait). The next 2 lines then set the values of the command and argument using the .next() function. This function (part of the iterator trait) returns the value at a saved index value then iterates that value. The full file path is formed by appending the previously set music path with the file sub-directory and name. The function unwrap_or(default) returns the normal value if no error, but returns the default if there is an error (empty string in this case). Line 39 is the beginning of match, which checks what matches and executes appropriately. If nothing matches, the default is _. The rest of the code is quite simple; reading file data, playing audio, stopping audio, error handling. 2.3 Command Line Interface

The code below sets up a Command Line Interface (CLI) which means the commands can be sent via a static terminal rather than connecting to the socket. This will probably make future GUI control simpler to code. This was written on a different file. The current file structure is as follows: the main directory is Cacofonix; within this directory there are daemon and cli directories (each of which have their respective main.rs (the code) and Cargo.toml (details & dependencies) files); within the Cacofonix directory there is another Cargo.toml file that references the other directories as part of a workspace. There are some other files but I don't know their purpose right now.

01 use std::os::unix::net::UnixStream;
02 use std::io::Write;
03 use std::env;
04 
05 const SOCKET_PATH: &str = "/tmp/music-daemon.sock";
06 
07 fn main() {
08 
09   let args: Vec<String> = env::args().skip(1).collect();
10 
11   if args.is_empty() {
12     eprintln!("Usage: strawberry <command> <argument>");
13     return;
14   }
15 
16   let command = args.join(" ");
17 
18   match UnixStream::connect(SOCKET_PATH) {
19     Ok(mut stream) => {
20       let msg = format!("{}"\n, command);
21       if let Err(e) = stream.write_all(msg.as_bytes()) {
22         eprintln!("Failed to send command : {}", e);
23       }
24     }
25     Err(e) => eprintln!("Connection failed : {}", e)
26   }
27 
28 }

Line 09 has quite a few new things. The collect() function can combine items into multiple types, so the variable type needs to be specified, which is done by : type = (this is also done for function inputs upon declaration, like in handle_command()). In this case the type is Vec<String> which is a list (dynamic size) of strings. Line 16 is the same as JavaScript; joins elements of args into one string with spaces (line 20 adds a \n to separate future commands). Line 21 only handles a potential error returned by stream.write_all() because if it works then there is nothing more for the program to do.

My idea is that the music-player can be used either by terminal or GUI. This means commands should be human-readable and there should be some way to give written feedback for terminal use (although not strictly necessary). I think that making a log file (e.g. at /tmp/cacofonix.log) would be a good solution because the user can send commands on their normal terminal, then read what is happening on a different terminal using tail -f /tmp/cacofonix.log (which prints the latest lines of a file as it updates). I can also used this file as a means of debugging later on. The daemon will also send commands through the socket for the GUI to pick up and be able to update live (e.g. when a file is confirmed to have started playing the song details will change).
